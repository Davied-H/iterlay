# AI 模型设置设计审视

方法：双路独立评审。A：/root/settings_design_review；B：/root/settings_evidence_review。A 完成设计判断后，才向主评审释放 B 的静态扫描结果。

目标：src/components/workbench/settings/AiModelsSettings.tsx，含模型概览、Codex 图片服务详情及周边设置导航。

核心判断：当前界面把底层配置对象排列整齐，但没有按用户要完成的任务组织。账号详情套用完整 API 配置表单，造成阅读层级过多、可操作信息过少、状态语义重复和密度失衡。继续压缩 padding 无法解决这些结构问题。

## 证据和适用范围

独立浏览器观察视口均为 1280×720，检查概览、Codex 图片编辑和默认图片模型下拉。未执行保存、测试连接、登录、退出、删除或真实持久化。

静态 detector 成功退出，结果 []，发现 0。仅说明静态规则没有命中，不能据此判定设计合理。浏览器 evaluate 仅允许只读，未注入检测脚本或创建覆盖层。

初始化控制台有 DialogTitle / Description 告警，但稳定 DOM 中对应 aria 引用均存在；需另行定位生命周期，不能宣称稳定页面缺少这些节点。

## 优先问题

### P1：页面骨架与实际任务不相称

Codex 图片详情实际只有服务名称需要填写，账号和 gpt-image-2 主要供查看，却依次呈现通用编辑标题、服务摘要、连接分组、账号卡片、模型分组、隐私说明和固定保存栏。模型说明仍说“选择或添加”，但没有对应入口。

影响：新用户需要理解整套配置框架才能发现能做什么；熟练用户查看账号也需要跳读多个分组。置信度：高。

修正：标题直接显示服务名称和用途；Codex 采用账号详情布局，以账号、状态、提供的模型为主；自定义 API 服务保留地址、密钥、模型的表单。只读模型明确标注由平台提供，无需配置。统一任务顺序，不强制共用全部章节。建议方向：shape、distill。

### P1：账号、服务、用途的对象关系仍不清楚

概览有两个同名 Codex / ChatGPT，只依赖次行的小字图片/文本区分；编辑和管理按钮的无障碍名称也同名。用户不知道这是两个账号、两个模型，还是同一账号的两个用途。

影响：可能重复添加、误进编辑页，或担心退出与删除的影响范围。置信度：高。

修正：保留现有独立连接的数据结构，用稳定可见的用途标识区分条目，并明确共享账号或独立连接的来源；可按账号或平台组织视觉分组，不借机迁移凭据模型。建议方向：clarify、shape。

### P1：登录、验证、保存状态混在一起

同页同时出现“账号已连接”、账号“已授权，可使用账号提供的模型”、模型绿色勾和“配置已保存”，另有“刷新状态”“检查连接”。默认服务可处于“未验证”。

影响：用户难判断已登录与确实可调用的差别，也难理解两个检查动作的范围。置信度：高。

修正：分别表达账号授权、连接验证与未保存修改；登录成功不直接承诺模型可用；固定模型不用成功勾号。检查连接保留一个明确入口，刷新登录等低频动作次级呈现。保留用户已确认的显式保存方式，无修改时不强化保存操作。建议方向：clarify、harden。

### P2：空间、字号、对齐线没有形成统一规则

编辑页页签起点 x323、返回图标 x301、标题 x337、正文 x368、字段 x528，概览原有的内容轴没有延续到详情。双栏说明宽140px，模型说明发生不自然换行。大量文字11px，内容区约710px宽，却只显示少量可操作信息。底栏72px，48px页头下仍有细小滚动，隐私说明末端被裁切。

影响：视觉呈现为空、碎、小；阅读依赖来回跳视。置信度：高。

修正：统一正文轴线与布局宽度。短表单使用纵向标签和自然内容高度；正文13–14px、辅助12px，减少重复说明和分隔线。编辑时弱化页面外的分类切换，使返回、服务身份和主操作形成明确层级。建议方向：layout、typeset。

### P2：概览优先级和组件密度不一致

默认模型区域约206px，连同导航标题约240px以上；“我的服务”从y429开始，首屏只见两条完整服务和第三条的一部分。添加按钮计算尺寸104×36、文字14px，与局部 CSS 声明的30px高、11px不符，说明实际样式仍受另一套组件规则控制。

影响：管理服务这一主要任务出现在首屏下方；单改局部 CSS 值无法确保整套控件协调。置信度：高。

修正：将默认模型保持为紧凑的三行路由摘要，使服务列表更早出现；基于共享组件建立统一尺寸，而非逐处覆盖。以实际计算样式和真实视口验收。建议方向：layout、polish。

## 值得保留

- 按图片、文本、视频选择默认模型，且同时显示模型和服务身份，符合创作任务。
- 中性色视觉、列表状态列的对齐、可见的账号邮箱和本机凭据范围说明。
- AI 设置与外部工具的区分有明确意义，主要问题在编辑页内部的结构和优先级。

## 用户视角

首次接入者需要先知道连接的是账号还是 API、下一步该做什么、是否能开始创作；当前同名服务和多个成功状态增加不确定性。

高频维护者需要快速看出当前账号、用途、模型与异常；通用长表单使主要信息分散，底部操作离内容过远。

## 协作修正

前几轮逐点压缩 padding、标题和按钮，但未把信息结构、状态定义和控件规范作为整体验收，因此局部变小，整体仍不协调。下一轮先锁定服务详情的阅读顺序与账号/API两类结构，再统一一轮落地与截图验收。

建议优先重做服务详情，以账号状态、可用模型、必要配置、显式保存为序；然后统一概览与详情的对象标识和控件密度。

## 后续需要选择的方向

- 编辑承载方式：保留设置弹窗内的聚焦详情，或改为右侧抽屉。
- 改造顺序：先解决服务详情与状态语义，或同时统一整套设置中的表单规范。
